## Technical decisions

### Phase 2 — foundations (2026-10-18)

| Decision | Why |
|---|---|
| **Light theme only.** `useTheme()` returns one palette; `app.json` sets `userInterfaceStyle: "light"`. The template's dark palette and `use-color-scheme` hooks were removed | The mockups have no dark variant. Inventing one is outside the brief |
| **Design tokens live in `src/constants/theme.ts`**, copied from the `DESIGN.md` front matter (`Colors`, `Typography`, `Radius`, `Spacing`, `Layout`). Letter spacing converted from em to px, radii from rem at 16px | One source of truth; `__tests__/theme-test.tsx` pins the key values |
| **Sora via `@expo-google-fonts/sora`**, weights 400/500/600/700, loaded with `useFonts` in the root layout. Text styles set `fontFamily` per weight, never `fontWeight` | On native a custom font family does not switch weight with `fontWeight` |
| **Custom tabs with `expo-router/ui`, one file for web and native**, not `NativeTabs`. The default tab bar is hidden and the visible bar is `SideNav` (window ≥ 768 px) or `BottomDock` (phones) | The mockups need a custom dock with a "+" action and a desktop side nav, which native tabs cannot draw |
| **Route layout:** root `Stack` → `(tabs)` group (Home, Calendar, Categories) and `task/new` as a stack route over the tabs | Keeps detail/form screens outside the tab bar, as planned |
| **No icons yet.** Tab labels are text and the action is a "+" glyph | Icon approach (Material Symbols as in the mockups) is decided in Phase 5 after reading the Expo icon docs |
| **Brand name "ToDo"** in the side nav, not the mockup's "TaskFlow / Monolith Core" | The project is called ToDo; the mockup name is sample copy. Change in one place (`side-nav.tsx`) if you want another |
| **Testing: `@testing-library/react-native` 13.3 + `react-test-renderer` 19.2.3 + `jest-expo` 57**, not RNTL 14 | Expo Router 57's `renderRouter` renders synchronously. The docs say SDK 57 works only with RNTL v13; v14 (async render) is for SDK 58+. Revisit when upgrading Expo |
| **`"types": ["jest", "node"]` in `tsconfig.json`** | TypeScript 6 no longer auto-includes `@types/*`, so `describe`/`expect` were unknown |
| **`config/jest/expo-router-matchers.d.ts`** declares `toHavePathname` and friends | Expo Router 57 registers the matchers at runtime but ships no typings |
| **`@/global.css` is mapped to an empty module in Jest** (`config/jest/style-mock.js`, kept out of `__tests__/` because jest-expo treats every file there as a test) | Jest cannot parse CSS |
| **ESLint added by `npx expo lint`** (`eslint@9`, `eslint-config-expo`, `eslint.config.js`) | The project rules require lint before a task is done; Expo installs its recommended config on first run |
| **Removed template files and unused assets**, and the `reset-project` script | They were demo content; the script moves/deletes source folders |
| **Typed routes: `.expo/types/router.d.ts` is generated by a running `expo start` and is git-ignored.** If `tsc` reports "`/` is not assignable to type …" the file is stale: delete it (without the file `Href` is a plain string and `tsc` passes) or let one dev server regenerate it | A dev server left running kept rewriting the file while files were added, and produced false route errors (the stale copy appeared while a leftover server from the browser preview was still running; after it was stopped and the file deleted it did not come back). Stop leftover dev servers before running `tsc` |

### Phase 3 — data contract (2026-10-18)

| Decision | Why |
|---|---|
| **ERD open point 4 accepted:** no authentication, so no per-user data protection. Firestore rules will validate shape and size only | Owner confirmed; a username is a handle, not a credential |
| **Domain types omit `userId`.** Ownership is the Firestore path `users/{username}/...`; repositories take `username` | Avoids repeating the path in every object and keeping the two in sync |
| **`domain/` is pure** (no Firebase, React, React Native or Expo imports) and `constants/` too. `__tests__/domain/purity-test.ts` enforces it, and also that no component or route imports `firebase` | The layer rule from the plan, as a test instead of a manual grep |
| **Stored statuses: `pending`, `in_process`, `done`.** `overdue` = not done and `dueAt` strictly before now (due exactly now is not overdue) | ERD correction 7 |
| **A done task is 100% whatever its subtasks say;** with subtasks progress = done ÷ total; without, 0% until done | ERD correction 8. "Finish Task" on 3/5 subtasks must read 100% |
| **`applyStatus` owns `completedAt`:** set when an item becomes done, cleared when it leaves done, kept when it stays done | One place for the rule, so every repository write behaves the same |
| **Username: 3–20 characters, `a-z 0-9 _`,** after trimming, dropping a leading "@" and lowercasing | Matches the sign-in mockup handles; becomes the Firestore document id. Not allowing "." or "-" keeps ids safe in paths and URLs |
| **Limits** (name 80, description 2000) live in `validation.ts` (`LIMITS`) and must be repeated in `firestore.rules` in Phase 4 | Single source for forms; rules cannot import code |
| **Category is required on a task;** a task's `startAt`, if set, must not be after `dueAt` | ERD ("Category REQUIRED" in the mockup) and the Calendar time range |
| **Priority/status chip colours** are theme tokens in `constants/priorities.ts` and `statuses.ts`: Low grey, Medium amber, High pink, Urgent red; Pending grey, In Process cyan, Done pink, Overdue red | Taken from `mobile_category_registry`, `mobile_status`, `home`. The mockups disagree in places (Medium is grey in `mobile_status`, "Normal" is cyan in `mobile_category_registry`); amber Medium matches the desktop Home "MID PRIORITY" chip |
| **Subtasks have their own `status`** (pending / in_process / done) although the UI only shows a checkbox | ERD lists a subtask status; the checkbox toggles pending ↔ done |

### Phase 4 — Firebase and database handlers (2026-10-18)

| Decision | Why |
|---|---|
| **Cloud Firestore, Standard edition, default database.** Created by the owner in the Firebase console | Simplest and cheapest fit for these queries. The `firebase-firestore` skill defaults new databases to Enterprise edition; Standard is enough here and is what `firebase.json` assumes |
| **`firebase` pinned to 12.19.0**, not 13 | Expo documents "12.0.0 and above". Version 13 needs Node 24.12+ for its packages and this machine runs Node 22. Revisit when Node is upgraded |
| **Config from `EXPO_PUBLIC_FIREBASE_API_KEY / PROJECT_ID / APP_ID`** in `.env.local` (git-ignored), template in `.env.example`; read lazily on first database use | Web config values are public identifiers; the rules, not secrecy, protect data. Lazy read keeps tests and builds working without configuration. On Netlify the same three variables go in the site settings |
| **Repositories behind interfaces** (`src/repositories/types.ts`) with two implementations: Firestore and an in-memory fake. UI code only sees the interfaces; Firebase is imported only in `services/firebase` and `repositories` (a test enforces it) | Component and hook tests use the fake; no UI code can depend on Firebase |
| **One shared contract test suite** (`config/jest/repository-contract.ts`, 29 cases) runs against the fake in every `npm test`, and against Firestore when the emulator is available | The fake is only trustworthy if the real implementation is held to the same behaviour |
| **Firestore implementation verified against the real project `todo-e618b` on 2026-10-18:** `npm run db:smoke` (14 checks) and `npm run test:firestore` (the full 29-case contract suite) both pass. The local emulator was not used (needs JDK 21+, this machine has Java 8) | The contract suite found two real bugs that the in-memory fake hid, both fixed (see next two rows) |
| **Rules bug found and fixed by the real run:** `allow read` used the document id (`isValidId(categoryId)`), which is not bound for list queries, so every list was denied. Reads are now split: `get` checks ids, `list` checks only the username | Only a real Firestore run could show this; the rules had compiled fine |
| **Updates check the document exists first** (`requireExisting`), so updating a missing document is `not-found`, not `permission-denied` | The rules read the existing document on update, so Firestore reports a missing one as a permission error. One extra read per update |
| **The real-Firestore contract run uses its own Jest config** (`config/jest/firestore.jest.config.js`, plain Node, Babel TypeScript + CommonJS) and `npm run test:firestore`. It creates `ct...` users and deletes them afterwards. `npm run db:cleanup -- <username>...` removes leftovers of an interrupted run | The jest-expo React Native environment cannot make Firestore network calls. Usernames cannot be listed (rules forbid it), so leftovers must be named |
| **Duplicate `@firebase/app` copies broke Firebase** (`Service firestore is not available`) after pinning `firebase` 12.19.0 over an earlier 13 install. Fixed with `npm dedupe`; if it returns, run `npm dedupe` again | Two copies of `@firebase/app` mean two component registries |
| **Dates use the client clock** (`now()` is injected), stored as Firestore Timestamps | Makes every test deterministic; skew is irrelevant for a to-do list |
| **No composite indexes.** Lists use equality or a single-field range, and are sorted in code. `firestore.indexes.json` stays empty | Avoids index deployment steps. Revisit if a query combines a filter and an order on different fields |
| **A task belongs to the calendar day of its `dueAt`** (local time zone); `listByDay` is a server-side range query on `dueAt` | One rule for Home "due today" and the Calendar |
| **Category delete is blocked while tasks use it** (`category-in-use`); the UI will offer to move or delete the tasks | Safest default; no silent data loss |
| **Subtask writes update the parent's counters in one transaction**, using `counterDelta` from the domain layer. Task delete also deletes its subtasks in batches of 400 | Progress rings need no read per subtask; counters can never drift from a single failed write |
| **Counters and completion are computed in one place** (`applyStatus`, `counterDelta`) and used by both implementations | No duplicated rules |
| **`RepositoryError` with 7 codes** is the only error the UI handles; Firestore errors are mapped (`permission-denied`, `unavailable`, `not-found`, `already-exists`, `invalid`) | UI code never depends on Firebase error shapes |
| **Rules are a prototype with no authentication**, audited in [`firestore-rules-audit.md`](firestore-rules-audit.md): score 1/5 for public use, accepted for this scope. They enforce shape, types, enums, limits and paths, and forbid listing users. Recommended extra steps outside the repo: App Check and a budget alert | There is no identity to check; see ERD open point 4 |
| **Rules syntax has not been machine-checked** | No emulator and no project. Verification steps are in the audit file |
| **Jest can import Firebase's `Timestamp`, but not run a real Firestore.** `transformIgnorePatterns` now also transforms `firebase` / `@firebase`, and `@firebase/util`'s `postinstall.mjs` is stubbed | Firebase ships ES modules; mixing its ESM and CJS builds in Jest creates two app registries ("Service firestore is not available"). Real Firestore is exercised by the emulator suite and `db:smoke`, which run outside Jest's module system |
| **`.firebaserc` points the CLI at the project** (`todo-e618b`); the project id is public, not a secret | `firebase deploy` needs no `--project` flag |
| **`tsx` added as a dev dependency** for `npm run db:smoke` | Runs a TypeScript script with the project's `@/` aliases |
| **User documents can be deleted by anyone** who knows the username | Needed for the smoke test's cleanup and for a future "delete my list"; equivalent to the access everyone already has |

### Phase 5 — reusable components (2026-10-18)

| Decision | Why |
|---|---|
| **Icons: `expo-symbols`' `SymbolView` through our own `Icon`** (`components/ui/icon.tsx`). One `ICONS` table maps each purpose (`add`, `clock`, `overdue`...) to the Material Symbols name from the mockups (web and Android) and an SF Symbol (iOS). No new icon package | `expo-symbols` 57 already depends on `@expo-google-fonts/material-symbols` and renders those names on web. Verified in the browser. `@expo/vector-icons` is documented as heading for deprecation |
| **Icons are hidden from screen readers.** A button's meaning comes from its `label`; `IconButton` requires one | An icon alone has no text |
| **Soft card style, not the hard-offset shadow.** Cards, inputs and the dock use `Shadow.card`; the mobile add-task mockup's 3px charcoal bottom edge is not reproduced | The updated desktop `add_task`, `add_subtask`, `home`, `calendar` mockups use soft shadows; the mobile add forms are the outliers |
| **Radius scale follows the mockup HTML** (`rounded-xl` = 12px), already what `Radius.md` is | `DESIGN.md` front matter lists a different scale (xl = 24px) than the Tailwind config in the same mockups |
| **Date-time input: browser `<input type="datetime-local">` on web** (`date-time-field.web.tsx`); phones use a typed "YYYY-MM-DD HH:mm" field | Web is the target. A native picker needs a package outside the web-first scope; add `@react-native-community/datetimepicker` later if phones matter |
| **`ProgressRing` uses `react-native-svg`** (added with `npx expo install`) | Draws the arc on web and native without platform code |
| **Category colour tint** = the category's `#rrggbb` plus an alpha byte (`withAlpha`) | Categories carry one user-chosen colour; the tinted pill and icon badge derive from it |
| **No images on category cards.** A folder icon on a tinted tile replaces the mockup illustrations | The ERD has no image field |
| **The mockup brand copy is not used:** "Create Mission", "Operational Calm", "Mission" become "New Task", "Add the details...", etc. | The product is a plain to-do list |
| **Forms are pure:** they take data and callbacks (`categories`, `now`, `onSubmit`) and never call repositories or read the clock. They validate with `domain/validation` and emit `NewTask` / `NewSubtask` / `NewCategory` | Phase 7 wires them to the data layer; tests need no Firebase |
| **A form's actions are rendered once:** header on desktop, bottom on phones. The mockup repeats Cancel/Save in a side card too | Duplicate buttons would confuse screen readers and tests; one set meets the same need |
| **Inline subtasks in the task form inherit the task's priority** and start with the task's due time; they are edited fully in the subtask form | The mockup's inline subtask rows have no priority control |
| **Quick add** (`QuickAddCard`): due end of today, medium priority, needs a name and a category | Owner-confirmed: "Fast Submit" stays disabled until a category is chosen |
| **Dev gallery at `/__gallery` and `/__gallery/forms`**, redirecting to Home when `__DEV__` is false; sample data in `src/dev/gallery-data.ts` | To compare every component with the mockups. Routes beginning with `__` are bundled, but unreachable in production builds |
| **`Button` and `IconButton` ignore a `style` injected by `<Link asChild>`** (their own props are applied last) | Otherwise a Link around a Button lost its styling |
| **Jest mocks `expo-symbols`** (`config/jest/setup.ts`) | The native icon module does not exist in Jest; icons are decorative |
| **Typed inputs expose an accessible name:** `TextField` / `TextArea` use their `label` as the accessible name unless one is given | Found by a test: spreading props after the label had erased it |
