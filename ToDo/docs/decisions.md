## Technical decisions

### Phase 2 — foundations (2026-10-18)

| Decision | Why |
|---|---|
| **Light theme only.** `useTheme()` returns one palette; `app.json` sets `userInterfaceStyle: "light"`. The template's dark palette and `use-color-scheme` hooks were removed | The mockups have no dark variant. Inventing one is outside the brief |
| **Design tokens live in `src/constants/theme.ts`**, copied from the `DESIGN.md` front matter (`Colors`, `Typography`, `Radius`, `Spacing`, `Layout`). Letter spacing converted from em to px, radii from rem at 16px | One source of truth; `__tests__/theme-test.tsx` pins the key values |
| **Sora via `@expo-google-fonts/sora`**, weights 400/500/600/700, loaded with `useFonts` in the root layout. Text styles set `fontFamily` per weight, never `fontWeight` | On native a custom font family does not switch weight with `fontWeight` |
| **Custom tabs with `expo-router/ui`, one file for web and native**, not `NativeTabs`. The default tab bar is hidden and the visible bar is `SideNav` (window ≥ 768 px) or `BottomDock` (phones) | The mockups need a custom dock with a "+" action and a desktop side nav, which native tabs cannot draw |
| **Route layout:** root `Stack` → `(tabs)` group (Home, Calendar, Categories) and `task/new` as a stack route over the tabs | Keeps detail/form screens outside the tab bar, as planned |
| **No icons yet.** Tab labels are text and the action is a "+" glyph | Icon approach (Material Symbols as in the mockups) is decided in Phase 5 after reading the Expo icon docs |
| **Brand name "ToDo"** in the side nav, not the mockup's "TaskFlow / Monolith Core" | The project is called ToDo; the mockup name is sample copy. Change in one place (`side-nav.tsx`) if you want another |
| **Testing: `@testing-library/react-native` 13.3 + `react-test-renderer` 19.2.3 + `jest-expo` 57**, not RNTL 14 | Expo Router 57's `renderRouter` renders synchronously. The docs say SDK 57 works only with RNTL v13; v14 (async render) is for SDK 58+. Revisit when upgrading Expo |
| **`"types": ["jest", "node"]` in `tsconfig.json`** | TypeScript 6 no longer auto-includes `@types/*`, so `describe`/`expect` were unknown |
| **`config/jest/expo-router-matchers.d.ts`** declares `toHavePathname` and friends | Expo Router 57 registers the matchers at runtime but ships no typings |
| **`@/global.css` is mapped to an empty module in Jest** (`config/jest/style-mock.js`, kept out of `__tests__/` because jest-expo treats every file there as a test) | Jest cannot parse CSS |
| **ESLint added by `npx expo lint`** (`eslint@9`, `eslint-config-expo`, `eslint.config.js`) | The project rules require lint before a task is done; Expo installs its recommended config on first run |
| **Removed template files and unused assets**, and the `reset-project` script | They were demo content; the script moves/deletes source folders |
| **Typed routes: `.expo/types/router.d.ts` is generated by a running `expo start` and is git-ignored.** If `tsc` reports "`/` is not assignable to type …" the file is stale: delete it (without the file `Href` is a plain string and `tsc` passes) or let one dev server regenerate it | A dev server left running kept rewriting the file while files were added, and produced false route errors (the stale copy appeared while a leftover server from the browser preview was still running; after it was stopped and the file deleted it did not come back). Stop leftover dev servers before running `tsc` |

### Phase 3 — data contract (2026-10-18)

| Decision | Why |
|---|---|
| **ERD open point 4 accepted:** no authentication, so no per-user data protection. Firestore rules will validate shape and size only | Owner confirmed; a username is a handle, not a credential |
| **Domain types omit `userId`.** Ownership is the Firestore path `users/{username}/...`; repositories take `username` | Avoids repeating the path in every object and keeping the two in sync |
| **`domain/` is pure** (no Firebase, React, React Native or Expo imports) and `constants/` too. `__tests__/domain/purity-test.ts` enforces it, and also that no component or route imports `firebase` | The layer rule from the plan, as a test instead of a manual grep |
| **Stored statuses: `pending`, `in_process`, `done`.** `overdue` = not done and `dueAt` strictly before now (due exactly now is not overdue) | ERD correction 7 |
| **A done task is 100% whatever its subtasks say;** with subtasks progress = done ÷ total; without, 0% until done | ERD correction 8. "Finish Task" on 3/5 subtasks must read 100% |
| **`applyStatus` owns `completedAt`:** set when an item becomes done, cleared when it leaves done, kept when it stays done | One place for the rule, so every repository write behaves the same |
| **Username: 3–20 characters, `a-z 0-9 _`,** after trimming, dropping a leading "@" and lowercasing | Matches the sign-in mockup handles; becomes the Firestore document id. Not allowing "." or "-" keeps ids safe in paths and URLs |
| **Limits** (name 80, description 2000) live in `validation.ts` (`LIMITS`) and must be repeated in `firestore.rules` in Phase 4 | Single source for forms; rules cannot import code |
| **Category is required on a task;** a task's `startAt`, if set, must not be after `dueAt` | ERD ("Category REQUIRED" in the mockup) and the Calendar time range |
| **Priority/status chip colours** are theme tokens in `constants/priorities.ts` and `statuses.ts`: Low grey, Medium amber, High pink, Urgent red; Pending grey, In Process cyan, Done pink, Overdue red | Taken from `mobile_category_registry`, `mobile_status`, `home`. The mockups disagree in places (Medium is grey in `mobile_status`, "Normal" is cyan in `mobile_category_registry`); amber Medium matches the desktop Home "MID PRIORITY" chip |
| **Subtasks have their own `status`** (pending / in_process / done) although the UI only shows a checkbox | ERD lists a subtask status; the checkbox toggles pending ↔ done |
